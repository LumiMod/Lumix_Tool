# 2026-11-24 实机实验记录

> 相机：Panasonic DC-S5（固件 2.9），服务模式 USB `04DA:2370`。
> 本次目标：验证 C payload 执行、尝试从相机侧读 SD 卡。

## 1. 已验证的成果

### C 编译的代码可以在相机上执行

用 ARM GCC 15.2.1 把 C 编译成 Thumb，注入 `0x86370000`，挂钩对焦音包装函数：

```
0x8F300010 = 0xCAFEBABE   ✅
```

这证明整条链路可用：**C 源码 → Thumb 二进制 → 注入 RAM → 执行**。

### `0x86370000` 区块确认安全

正常拍照 + 回放之后，`0x86370000..0x863B0000` 仍然是**全零**——
说明固件在运行时不使用这块区域，可以安全地放程序（256 KiB）。

### 从 payload 调用 SD 驱动不会崩相机

三种探针都正常返回（相机没死机），说明调用机制本身是通的。

## 2. 没打通的：相机侧读 SD

### 三次探针的结果

| 探针 | 参数 | 返回 | 缓冲 |
|---|---|---|---|
| `sd_probe` | r1 = 指向「偏移量 0」的指针 | 10 | 未写 |
| `sd_probe2` | r1 = 指向「虚拟缓冲地址」的指针 | 0 | 仍为零 |
| `sd_probe3` | r1 = 指向「物理缓冲地址」的指针 | 10 | 未写 |

### 原因分析

反汇编 `SDD_Read`（`0x863C0504`）发现：

1. 函数开头 `ldr r1, [sl]` 会解引用第一个参数指向的字，**为 0 直接走错误路径**（这解释了 probe 1 的返回 10）。
2. 真正的数据通道不是简单缓冲区：函数把 `r2` 当作**请求对象数组**（2 个指针，8 字节步进），
   对每个对象写 `+0x20` 和 `+0xD8` 字段。

也就是说 `SDD_Read` 是**命令提交函数**，不是"读扇区"接口。要调用它，必须先构造
符合驱动的请求对象（含 DMA 描述），这是另一个量级的逆向工作。

### 挂钩观察真实参数的尝试失败

把日志钩子装到 SD 读包装函数 `0x863CA4BE` 上，然后回放/拍照：

- 相机**黑屏并自动重启**（两次）
- 重启后钩子被恢复、日志区被清空
- 拔电池彻底复位后，回放恢复正常

**结论**：这个钩子点不安全（可能在受限栈上下文里被调用），不能用来观察参数。

## 3. 接口稳定性问题

服务模式 USB 在**大量读取**时会卡死：

- 小范围读取（几十个 1 KiB 块）正常
- 64 MB 扫描在第 2 块就失败（`bulk IN failed, GetLastError=31`）
- 卡死后 `CreateFile` 返回 5，需要**拔插 USB 线**才能恢复（不用重启相机）
